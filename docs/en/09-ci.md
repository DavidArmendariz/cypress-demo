# 9. Continuous integration

*[English](../en/09-ci.md) · [Español](../es/09-ci.md)*

- CI runs the same commands you run locally. No CI-only scripts.
- Start servers with your process manager, never from inside a spec.
- Split fast feedback (types, lint) from slow feedback (browsers) into separate jobs.

## Job structure

| Job | Runs | Why separate |
|---|---|---|
| Static | type check, lint | Seconds. Catches most mistakes before a browser starts. |
| End-to-end | the full browser suite | Minutes. Needs the application running. |
| Component | component specs | No servers needed, so it runs in parallel. |

Run them concurrently. Total wall time is then the slowest job, not the sum.

## Starting servers

```yaml
- uses: cypress-io/github-action@v7
  with:
    start: npm run dev
    wait-on: 'http://localhost:5180, http://localhost:3001/api/health'
    wait-on-timeout: 120
```

The action installs dependencies, caches the Cypress binary, boots the servers, waits for them to
answer, runs the suite, and shuts everything down.

Give the API a trivial `/api/health` endpoint for `wait-on` to poll. Waiting on the client alone is
not enough: a dev server can be serving HTML while the API behind it is still starting.

Locally, `start-server-and-test` does the same job:

```bash
start-server-and-test dev http://localhost:5180 'cypress run'
```

Starting a server from inside a spec with `cy.exec()` or `cy.task()` leaves orphaned processes,
causes port conflicts on reruns, and gives you nothing useful when the server fails to boot.

## Secrets

```yaml
env:
  CYPRESS_testUserEmail: qa-user@example.com
  CYPRESS_testUserPassword: ${{ secrets.TEST_USER_PASSWORD }}
```

`CYPRESS_<name>` populates the Cypress environment, and `cy.env(['testUserPassword'])` reads it
exactly as it reads the local file. See [07-secrets-and-env.md](07-secrets-and-env.md).

## Artifacts

```yaml
- uses: actions/upload-artifact@v7
  if: failure()
  with:
    name: cypress-screenshots
    path: cypress/screenshots
    if-no-files-found: ignore
    retention-days: 7
```

`if: failure()` only. Uploading artifacts from green runs is pure cost.

Leave video off by default. It is slow to record, large to store, and screenshots plus the command
log answer most questions. Turn it on for a specific investigation.

## Retries

```ts
retries: { runMode: 2, openMode: 0 }
```

CI retries, local runs do not. A test that only passes on attempt three is still broken. Retried
tests are flagged in the run summary, and that flag is a bug report, not a green build. Review it
weekly or it becomes wallpaper.

## Pull requests vs main

Run the full suite on pull requests, so failures are attached to the change that caused them. Running
only on `main` means you find out after merging, when it is somebody else's problem too.

Use `concurrency` to cancel superseded runs on the same branch:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

## Scaling up

When the suite grows past roughly ten minutes, parallelise before people start skipping it. Cypress
Cloud provides load balancing across containers, automatic cancellation on first failure, and flake
detection:

```yaml
strategy:
  matrix:
    containers: [1, 2, 3]
# with:
#   record: true
#   parallel: true
```

Add it when the runtime justifies it, not before. Below ten minutes the coordination overhead is
usually larger than the saving.

## One command

Define a single entry point that runs everything, and have CI call exactly that:

```bash
make verify   # types + lint + component + end-to-end
```

If it is green on your machine, CI will not surprise you with a different command. See
[11-makefile-as-entrypoint.md](11-makefile-as-entrypoint.md).
