# 9. CI

*[English](../en/09-ci.md) · [Español](../es/09-ci.md)*

- CI ejecuta los mismos comandos que ejecutas en local. Ningún script exclusivo de CI.
- Arranca los servidores con el gestor de procesos, nunca desde dentro de una spec.
- Separa el feedback rápido (tipos, lint) del lento (navegadores) en trabajos distintos.

## El workflow

`.github/workflows/ci.yml` tiene tres trabajos:

| Trabajo | Ejecuta | Por qué va aparte |
|---|---|---|
| `static` | `npm run typecheck`, `npm run lint` | Segundos. Detecta la mayoría de errores antes de arrancar un navegador. |
| `e2e` | `cypress-io/github-action` con `start` y `wait-on` | Minutos. Necesita los dos servidores. |
| `component` | la misma action con `component: true` | No necesita servidores, así que corre en paralelo. |

Se ejecutan en paralelo, así que el tiempo total es el del trabajo más lento, no la suma.

## Arrancar los servidores

```yaml
- uses: cypress-io/github-action@v6
  with:
    start: npm run dev
    wait-on: 'http://localhost:5180, http://localhost:3001/api/health'
    wait-on-timeout: 120
```

La action instala dependencias, cachea el binario de Cypress, arranca los servidores, espera a que
ambos respondan, ejecuta la suite y lo apaga todo. `/api/health` existe en `server/app.ts` justo para
esto.

Arrancar un servidor desde dentro de una spec con `cy.exec()` o `cy.task()` deja procesos huérfanos,
provoca conflictos de puertos en las reejecuciones y no te da ninguna salida útil cuando el servidor no
arranca. En local ese mismo trabajo lo hace `start-server-and-test`, conectado en el target `e2e` del
`Makefile`.

## Secretos

```yaml
env:
  CYPRESS_testUserEmail: demo@example.com
  CYPRESS_testUserPassword: ${{ secrets.TEST_USER_PASSWORD || 'Password123!' }}
```

`CYPRESS_<nombre>` rellena el entorno de Cypress, y `cy.env(['testUserPassword'])` lo lee exactamente
igual que lee `cypress.env.json` en local. Ninguna spec se ramifica según el entorno. Ver
[07-secrets-and-env.md](07-secrets-and-env.md).

## Artefactos

```yaml
- uses: actions/upload-artifact@v4
  if: failure()
  with:
    name: cypress-screenshots
    path: cypress/screenshots
```

Solo `if: failure()`. Subir artefactos de ejecuciones verdes es coste puro. El vídeo está desactivado en
`cypress.config.ts`: es lento de grabar, grande de almacenar, y las capturas más el command log
responden a casi todas las preguntas. Actívalo para una investigación concreta.

## Reintentos

`retries: { runMode: 2, openMode: 0 }`. CI reintenta, las ejecuciones locales no. Una prueba que solo
pasa al tercer intento sigue estando rota, y una prueba reintentada se marca en el resumen de la
ejecución. Trata esa marca como un informe de error, no como una build verde.

## Paralelismo

Comentado en el workflow, porque necesita una record key de Cypress Cloud:

```yaml
# record: true
# parallel: true
# y una matriz de `containers: [1, 2, 3]` en este trabajo
```

Con 2 minutos para 41 pruebas esta suite no lo necesita. Añádelo cuando la suite crezca, no antes.
Cloud da además balanceo de carga, cancelación automática al primer fallo y detección de inestabilidad,
que es donde está el valor real.

## Todo de una vez

```bash
make verify   # typecheck + lint + e2e + component
```

El mismo target en local y en revisión. Si `make verify` está verde en tu máquina, CI no te va a
sorprender con un comando distinto.
