# 9. CI

- CI runs the same commands you run locally. No CI-only scripts.
- Start servers with the process manager, never from inside a spec.
- Split fast feedback (types, lint) from slow feedback (browsers) into separate jobs.

## The workflow

`.github/workflows/ci.yml` has three jobs:

| Job | Runs | Why separate |
|---|---|---|
| `static` | `npm run typecheck`, `npm run lint` | Seconds. Catches most mistakes before a browser starts. |
| `e2e` | `cypress-io/github-action` with `start` and `wait-on` | Minutes. Needs both servers. |
| `component` | the same action with `component: true` | No servers needed, so it runs in parallel. |

They run concurrently, so total wall time is the slowest job, not the sum.

## Starting servers

```yaml
- uses: cypress-io/github-action@v6
  with:
    start: npm run dev
    wait-on: 'http://localhost:5180, http://localhost:3001/api/health'
    wait-on-timeout: 120
```

The action installs dependencies, caches the Cypress binary, boots the servers, waits for both to
answer, runs the suite, and shuts everything down. `/api/health` exists in `server/app.ts` for
exactly this.

Starting a server from inside a spec with `cy.exec()` or `cy.task()` leaves orphaned processes,
produces port conflicts on reruns, and gives you no useful output when the server fails to boot.
Locally the same job is done by `start-server-and-test`, wired up in the `e2e` target of the
`Makefile`.

## Secrets

```yaml
env:
  CYPRESS_testUserEmail: demo@example.com
  CYPRESS_testUserPassword: ${{ secrets.TEST_USER_PASSWORD || 'Password123!' }}
```

`CYPRESS_<name>` populates the Cypress environment, and `cy.env(['testUserPassword'])` reads it
exactly as it reads `cypress.env.json` locally. No spec branches on environment. See
[07-secrets-and-env.md](07-secrets-and-env.md).

## Artifacts

```yaml
- uses: actions/upload-artifact@v4
  if: failure()
  with:
    name: cypress-screenshots
    path: cypress/screenshots
```

`if: failure()` only. Uploading artifacts from green runs is pure cost. Video is off in
`cypress.config.ts`: it is slow to record, large to store, and screenshots plus the command log
answer most questions. Turn it on for a specific investigation.

## Retries

`retries: { runMode: 2, openMode: 0 }`. CI retries, local runs do not. A test that only passes on
attempt three is still broken, and a retried test is flagged in the run summary. Treat that flag as a
bug report, not as a green build.

## Parallelism

Commented out in the workflow, because it needs a Cypress Cloud record key:

```yaml
# record: true
# parallel: true
# and a matrix of `containers: [1, 2, 3]` on this job
```

At 2 minutes for 41 tests this suite does not need it. Add it when the suite grows, not before.
Cloud also gives load balancing, auto-cancellation on first failure, and flake detection, which is
where the actual value is.

## Everything at once

```bash
make verify   # typecheck + lint + e2e + component
```

Same target locally and in review. If `make verify` is green on your machine, CI is not going to
surprise you with a different command.
